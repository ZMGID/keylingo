# 侧栏分组顺序由用户手排，不按时间

侧栏里集和项目的上下顺序完全由用户拖拽决定：索引文件里的数组顺序就是显示顺序，读取时不做任何排序。集本来就是这个行为；项目原先在每次列举时按 `updated_at` 倒序重排，该排序已删除——它排的其实是「上次重命名 / 改描述 / 改颜色 / 改根目录的时间」（`project.updated_at` 只在显式编辑时写入，与在该项目下聊天无关），作为「最近使用」信号是假的。

集/项目**展开后的对话**也能拖，但规则不同：那里**时间序仍是底座**，被拖过的对话钉在用户放的那一行，其余按更新时间填剩下的空位。「最近」平铺列表不可拖。

## Considered Options

- **对话列表也整体改成手排**：否决。「最近」这个 tab 的语义就是时间线，整体手排会让它名不副实，也丢掉「昨天聊的那个在哪」这个入口。所以「最近」**不可拖**、永远时间序。
- **集/项目里的对话整体切成手排**：否决。最终选的是「时间序做底座 + 钉子」：拖过的对话钉在你放的那一行，其余仍按更新时间填剩下的空位（`src/chat/conversationPins.ts`）。代价是被钉项的邻居会随时间变化——当时明确权衡过并接受。
- **保留时间排序 + 另加一个手动 `order` 字段做覆盖（分组行）**：否决。集和项目从此规则不同，而且等于把分组行也拖进上面那套混合序。
- **两边都改成显式 `order` 整数字段**：否决。要给两份索引文件加字段 + 写迁移，还要处理 `order` 重复和空洞，而数组顺序已经够用。
- **让位式拖拽（其余行上下让位，供应商列表那套）**：否决。它要求所有行等高，而分组行可展开、对话行高度也不齐。改用插入线式（`src/utils/insertionReorder.ts`）：只有被拖那行浮起，其余行不动，目标位置画一条线，按每行真实位置做命中判定，因此不要求等高，也不需要「拖拽时先把分组全折叠」那种 hack。

## Consequences

- **不要给 `get_projects` / `get_sets` 加回任何排序。** 加回去会静默抹掉用户手排的顺序，没有任何报错，用户只会觉得「我排的怎么又乱了」。
- 分组行的重排命令只接收一个 id 顺序数组，后端自己 load 索引 → 按 id 重排 → 存回，不覆盖任何其它字段（与 MCP server 保存时的 read-fresh-then-merge 同理：别把别处的改动冲掉）。认不出的 id 忽略；id 数组没提到的项保持原有相对顺序、排在最前面——会出现这种情况的现实场景只有「前端取完列表之后别处又新建了一个」，而新建就是插最前，放最前正好一致。
- 对话的钉子单独存在 `conversations/conversation-pins.json`（`group_id → [{id,row}]`），**没有加到 `ChatProject`/`ChatSet` 上**：那两个结构有多处构造点，加字段要挨个改且会动到已有序列化。显示顺序在前端算（嵌套列表本来就是前端拼的），后端只负责存。
- 升级后老用户的项目顺序会一次性变化（从「上次编辑时间倒序」变成索引文件里既有的数组顺序）。不丢数据。
- 新建的集/项目仍然插在最前面——刚建的马上要用。代价是用户排在第一位的那个每次新建都被挤下一格。
